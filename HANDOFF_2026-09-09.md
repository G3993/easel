### The old Canvas MIDI knob/fader bank was removed from Canvas
- `Application::renderCanvasKnobBank()` (pre-existing, not written this session) used to
  render a 3×8-knob + 8-fader MIDI CC bank under the Canvas viewport. Per a late request,
  **the call site was removed** (`Application.cpp`, was around line 4586) and the extra
  `kCanvasKnobBankH` reserved-space logic in the dockspace setup was deleted too. The
  function itself is still **defined but now dead code** — left in place rather than
  deleted, since its MIDI-CC-binding logic (`m_knobTarget`, `MIDIMapping::Target`,
  `m_dataBus.bind`) might be depended on elsewhere and wasn't fully traced. If confirmed
  truly unused, it and its associated members (`m_knobValue`, `m_faderValue`,
  `m_knobTarget`, `m_knobBoundParam`, etc. in `Application.h`) are candidates for deletion.
  **The Show Deck's knobs are a separate, simpler, unbound implementation** — not a
  continuation of the Canvas bank's MIDI binding.

### Thumbnail bug + fix (real gotcha, will recur if touched carelessly)
- Shader thumbnail generation/loading lived entirely inside the Sources→Shaders tab's
  render code (`Application.cpp`, guarded by `if (sourcesTabsOpen && sourcesActiveSub ==
  ST::Shader)`), which only runs while that panel is actually open. Once the right dock
  started defaulting to collapsed (see below), that code stopped running altogether, so
  the Show Deck's thumbnail rails went blank.
- Fix: added `lazyLoadCachedThumb()` inside `renderShowDeck()` that reads the **same**
  on-disk PNG cache (`~/.easel/shader_thumbs/<stem>.png`, i.e.
  `%USERPROFILE%\.easel\shader_thumbs\` on Windows) directly, independent of whether
  Sources has ever opened. It only *reads* — a shader with no cached PNG yet still needs
  Sources opened once to render+cache its first thumbnail.

## Two new "collapse tab" widgets
Both were built as **standalone always-rendered floating ImGui windows**, not widgets
embedded in the panel they control — because the panel they'd control either stops being
called entirely once collapsed (Timeline) or shrinks to near-nothing (right dock), so an
embedded button would become unclickable exactly when you need it to reopen. This pattern
should be reused for any future collapse UI in this codebase.

1. **`Application::renderTimelineCollapseTab()`** — small chevron tab centered
   horizontally, sitting on the seam between the transport pill and the timeline's top
   edge (both already meet there — same Y formula in both). Click toggles
   `m_timelineMinimized`. Styled per iterative feedback: half-height (8px), lighter grey
   bg, 2px border, wide (10px half-width) hand-drawn arrow (not `lucide::chevronUp/Down`
   — needed independent width/height control the shared icon fn doesn't offer).
2. **`Application::renderRightPanelCollapseTab()`** — narrow vertical tab on the **left**
   edge of the right Properties/Audio/MIDI dock, vertically centered. Click toggles
   `m_ui.rightDockCollapsed()` via new `UIManager::setRightDockCollapsed(bool)`.
   - Needed two new **always-valid** `UIManager` fields since the existing
     `m_rightFloatLeft` zeroes out when collapsed (a "no panel" signal for canvas-fit
     code): `m_rightFloatLeftRaw` / `rightPanelLeftRaw()` and `m_rightFloatCenterY` /
     `rightPanelCenterY()`.

**Z-order gotcha (documented in code, easy to re-break):** `renderFloatingTransportPill()`
calls `ImGui::BringWindowToDisplayFront` on itself *every frame*. Any new floating window
positioned near it (like the timeline tab) will render *underneath* it unless you also
explicitly `BringWindowToDisplayFront` your window, called *after* the pill's own render
call. Both new tabs do this; see the call sites right after
`renderFloatingTransportPill()` in `Application::renderUI()`.

**ImGui cursor gotcha (also documented in code):** `EndChild()`/`Dummy()` reset the
window's cursor X back to the content indent, not to wherever you last explicitly set it
with `SetCursorScreenPos`. Every place in `renderShowDeck()` that needs a specific X after
one of these calls re-issues `SetCursorScreenPos` explicitly — skipping that is exactly
the bug that made the right shader rail render in the wrong place earlier this session.

## Right dock now actually collapses (not just hides content)
Previously "collapsing" the right dock kept it full-width, just shrank its height to a
thin strip — so canvas/ShowDeck consumers reading `m_ui.rightRailWidth()` never reclaimed
the space. Now:
- `UIManager` computes a `rightWActual` (real current footprint: 8px sliver when
  collapsed, full `rightW` otherwise) and assigns it to `m_rightFloatW` — so
  `rightRailWidth()` and `getRightPanelLeft()` are honest in every state.
- The host window (`##RightFloatHost`) is still submitted while collapsed (kept the
  existing "must still render or DockSpace-skip orphans docked windows" safety), just at
  the 8px sliver size, and the inner pill nav bar is skipped while collapsed (the floating
  edge tab is now the primary way back in).
- Both the Timeline and the right dock **default to collapsed on every launch** —
  forced explicitly at the end of `Application::init()`
  (`m_timelineMinimized = true; m_timelineAnimT = 0.0f; m_ui.setRightDockCollapsed(true);`)
  rather than relying on the member-default alone, since a mode-transition hook
  ("entering Show pops the timeline open") could otherwise interfere.
